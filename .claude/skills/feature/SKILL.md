# feature — стадии задачи Tsudoi

Процесс перенесён из Hibiki. Бриф → продукт (если нужен) → техника → план →
реализация и QG → проверка владельцем → вливание через PR.
Сначала прочти [AGENTS.md](../../../AGENTS.md),
[видение](../../../.ai/vision.md) и README текущей задачи.

## Состояние и разрешённый объём

- Папка: `.ai/features/NN-slug/`. Статус во frontmatter `README.md`:
  `track`, `stage`, `branch`, `pr`. Стадии:
  `brief → product → tech → plan → build → review → merged`.
- Прежде чем создавать новую задачу, проверь существующую и её бриф. Не начинай
  уже сохранённую задачу заново. На «статус» покажи текущую стадию и следующий шаг.
- Если владелец явно ограничил текущий заказ документами, делай документы;
  план с автоматическим переходом к коду и реализацию начинай после его сигнала.
  Для 01-mvp это ограничение записано в её README и brief.md.
- Прямое разрешение «реализация» после обсуждения продукта/техники относится
  к изложенному объёму: запиши подтверждение и продолжай, не спрашивая то же снова.
  Не выдавай собственные предложения за ответы владельца.
- Без «принято»/«вливай» не вливай PR, кроме явного автономного режима этой задачи.

## Ветки и файлы

- Ветки: `codex/NN-slug`. Номер = max номеров папок на main и активных веток
  `codex/*` + 1; перед выбором проверь remote branches без переключения дерева.
- Сначала проверь `git status`. Не теряй чужие изменения. Для новой задачи на чистом
  дереве: обнови main fast-forward и создай ветку; для существующей продолжай её ветку.
- Работа по умолчанию в основном checkout: ворктри не получает storage/env/dependencies
  и может конфликтовать с локальными серверами. Если изоляция уже есть, учитывай её.
- [Шаблоны](templates/) — для README, брифа, продукта, техники, плана и проверки.
- Чекбоксы отмечают пройденные стадии. Черновик `product.md` публикуется со
  `stage: product` до подтверждения владельца. Переходы `product → tech`,
  `tech → plan`, `plan → build`, `build → review` и `review → merged` записывай
  после соответствующего подтверждения или выполненной работы.

## Треки

| Трек | Когда | Стадии |
|---|---|---|
| product | Меняются пользовательские возможности, UI или внешний API | Все |
| tech | Инфраструктура/рефакторинг без изменения продукта | Без product |
| Мелочь | Опечатка, небольшая документальная правка | Ветка → правка → проверка → PR |

Трек объясни одной фразой. Первичная основа и постановка 01-mvp публикуются
в `main` по поручению владельца. Для продолжения 01-mvp создай `codex/01-mvp` из `main`.

## 0. Бриф

1. Создай папку/README/brief в ветке, если задача ещё не заведена.
2. Запиши слова владельца дословно. Уточняй только существенное, по одному-двум
   вопросам; свои допущения помечай явно.
3. Опиши успех и не-цели, трек, разрешённый сейчас объём и режим работы.
4. Коммит `docs(NN): brief`, следующая стадия product или tech.

## 1. Продукт

- Сценарии, цель, не-цели, границы MVP, критерии провала и приёмка.
- Решения P01…: вопрос → варианты → рекомендация → решение владельца.
  До ответа последнее поле явно обозначает предложение, а не подтверждение.
- Можно использовать brainstorming, но результат — в product.md задачи,
  не в `docs/superpowers/`.
- Гейт: «продукт ок» или иное прямое подтверждение изложенного продукта.
  Затем коммит `docs(NN): product decisions`, stage tech.

## 2. Техника

- Прочти карточки затронутых зон [карты](../../../.ai/map/README.md), затем код.
  «Исходная система» описывает только проверенное; будущие пути помечаются будущими.
- Решения T01… тем же форматом; сторонние API/библиотеки сверяй с первичной документацией.
- Для Tsudoi проверь членство, срок и отзыв гостевого доступа, права на вложения,
  порядок событий, восстановление после обрыва связи и повторы отправки.
- Перечисли меняющиеся карточки и проверки живых поверхностей.
- Гейт: «техника ок» или прямое разрешение реализации обсуждённого объёма.
  Затем коммит `docs(NN): tech decisions`, stage plan.

## 3. План

- plan.md: задачи с файлами, содержательными проверками и критерием «готово».
- Последняя задача — знания: карточки зон и AGENTS соответствуют итоговому коду.
- Отдельного гейта после плана нет. Коммит `docs(NN): plan`, stage build,
  короткое сообщение владельцу и реализация. Явное ограничение «пока только доки»
  имеет приоритет до отменяющего его сигнала.

## 4. Реализация и QG

1. Реализуй по плану, новое поведение — через тест с наблюдаемым красным результатом.
   Отмечай задачи и делай отдельный коммит на законченное изменение, например `feat(chat): …`.
2. Пройди [verify](../verify/SKILL.md): свежая тройка и живые поверхности.
   В verify.md — факты, числа, ограничения и пути к доказательствам в storage.
3. Свежее ревью диффа: отдельный ревьюер/доступный review-инструмент.
   Существенное исправь и перепроверь, оставшееся объясни в verify.md.
4. Заполни «Что посмотреть руками», push ветки и PR через gh.
   Заголовок: `NN: <название>`; описание: проблема/поведение, документы, проверки и приёмка.
5. README: pr и stage review; коммит/push. Владелец получает PR и конкретные шаги проверки.

## 5. Проверка владельцем

Замечания — в той же ветке и verify.md; после исправлений свежий QG.
Гейт — явное «принято»/«вливай». Не выводи его из молчания, срочности или запроса статуса.

## 6. Вливание

После принятия проверь карточки и QG, допиши строку в
[историю](../../../.ai/history.md), отметь дату/stage merged, commit/push,
merge PR и обнови main. Если merge не состоялся, сообщи фактическое состояние,
не объявляй задачу влитой.

## Последний этап — деплой

После вливания версии приложения вызови [deploy](../deploy/SKILL.md). Если workflow уже запускает выкладку после merge, дождись его результата. Для правок только документации достаточно результата сборки, когда версия приложения на VPS не меняется.

`merged` фиксирует состояние Git. В отчёте по задаче укажи ссылку на job `deploy`, проверенный SHA и результат живой проверки. При ошибке job укажи фактическую версию на VPS.

## Автономный режим

Только явное «делай автономно» или аналогичное разрешение для конкретной задачи.
Дословно запиши его в brief.md и README. Тогда агент сам принимает и фиксирует
P/T-решения, проходит план, реализацию, QG, свежее ревью, PR и merge без гейтов.
Красный QG или существенное неустранённое замечание останавливают вливание.
Вопрос, явно оставленный владельцем за собой, остаётся его решением.
Разрешение на следующую задачу не переносится. Текущее разрешение проверяй в README/brief задачи.

## Попутные находки

Связанное небольшое исправляй в рамках задачи с записью в verify.md.
Остальное — в «Хвосты» README, без самовольного заведения новых задач.
Доки и общение — по-русски; код и conventional-коммиты — по-английски.
